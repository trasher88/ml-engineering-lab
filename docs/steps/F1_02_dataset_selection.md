# F1.2 - Dataset Selection & Provenance: выбор и фиксация датасета

## 1. Цель этапа:

После F1.1 появилась основа ML-проекта: структура каталогов, конфигурации, общие операции чтения и записи файлов, механизм проверки контрольных сумм и автономные тесты. Но пока непонятно: **на каких данных будет учиться модель и какой правильный ответ ожидается от неё получить**.

Решино построить систему, способную классифицировать технические вопросы по тематике. Например, текст о работе с SQL должен чаще относиться к области баз данных, а вопрос о правах доступа к файлам - к Linux. Для такого эксперимента нужны не просто случайные тексты, а примеры, у которых можно определить целевую категорию.

Вместе с тем проект задуман как последовательное изучение ML и LLM. В следующих фазах понадобятся не только вопросы и их темы, но и ответы: для поиска похожих случаев, retrieval/RAG и небольших экспериментов с обучением языковой модели. Поэтому выгодно заранее выбрать **один корпус, который подходит для нескольких учебных задач**, и не менять предметную область при каждом переходе к новой технологии.

Возникла ещё одна проблема: публичный репозиторий должен содержать проверяемое описание данных, но нет возможности без оговорок публиковать чужие тексты вопросов и ответов. Нужны метаданные, по которым можно установить источник и повторить процедуру, не добавляя сами Q&A-записи в Git.

**Задача F1.2:** обосновать выбор датасета, зафиксировать его конкретную версию и состав, определить смысл меток и ограничений, а также написать код, который проверяет эти сведения без сетевых запросов.

## 3. Последовательность действий

### Шаг 1. Сформулирована задача классификации и требования к данным
Первая ML-модель должна: **получить текст технического вопроса и выбрать одну из четырёх тематических категорий**. В терминах машинного обучения это *supervised multiclass classification*: на обучении есть текст (`X`) и известная метка (`y`), а на новом примере модель должна предсказать метку самостоятельно.

Для этого желательно иметь реальные технические тексты, похожие на вопросы пользователей, а также понятный способ сформировать метку класса. Но одних меток недостаточно: в будущих фазах понадобятся ответы, чтобы изучать поиск релевантных материалов и варианты post-training.

Поэтому сформулированы два требования к исходному корпусу:
1. У примера должен быть технический вопрос и источник, по которому можно построить учебную тематическую метку.
2. Должны существовать связанные с вопросом ответы, которые позднее можно использовать в отдельных экспериментах с учётом ограничений качества и лицензирования.

**Зачем этот шаг:** выбрать данные под конкретную задачу, а не просто скачать большой популярный датасет.

### Шаг 2. Выбрали выгрузку Stack Exchange на Hugging Face
Выбран датасет [Stack Exchange title/body and voted answers](https://huggingface.co/datasets/flax-sentence-embeddings/stackexchange_titlebody_best_and_down_voted_answer_jsonl).

Один пример в такой выгрузке связан с техническим вопросом и вариантами ответа. В исходной схеме интересуют три поля:

| Поле в исходном JSON | Содержание                                     | Возможное учебное применение                             |
| -------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| `title_body`         | Заголовок и тело технического вопроса          | Вход классификатора; запрос к поиску                     |
| `upvoted_answer`     | Ответ с более положительной оценкой сообщества | Кандидат в ответ для retrieval/SFT                       |
| `downvoted_answer`   | Ответ с менее положительной оценкой сообщества | Возможный контрастный пример для preference-эксперимента |

На последующем этапе загрузки F1.3 исходные поля преобразуются в рабочие `context`, `answer` и `rejected`. **Здесь только определен смысл полей и зафиксирована ожидаемая схема.**

Важно не сделать неверный вывод из названий: *upvoted* не равно «проверено экспертом как правильное», а *downvoted* не обязательно означает «заведомо неверное». Оценки пользователей дают шумный сигнал предпочтения, который требует осторожной интерпретации.

**Зачем этот шаг:** получить единый предметный корпус, пригодный как для первой классификации, так и для дальнейших учебных задач.

### Шаг 3. Выбраны четыре сообщества и определены метки
Сопоставлены четыре источника Stack Exchange четырём категориям, которые будет предсказывать классификатор.

| Сайт / исходный файл                    | Метка `domain` | Доступно после проверки обязательных полей | Выбрано для исходного эксперимента |
| --------------------------------------- | -------------- | -----------------------------------------: | ---------------------------------: |
| `unix.stackexchange.com.jsonl.gz`       | `linux`        |                                      6 173 |                                800 |
| `dba.stackexchange.com.jsonl.gz`        | `databases`    |                                      2 502 |                                800 |
| `serverfault.com.jsonl.gz`              | `systems`      |                                      7 969 |                                800 |
| `codereview.stackexchange.com.jsonl.gz` | `programming`  |                                        666 |                                666 |
| **Всего**                               | **4 класса**   |                                          — |                          **3 066** |

При первоначальном формировании поднабора использовано правило: `seed=42` и **не более 800 валидных записей от каждого сообщества**. Из первых трёх источников взяли по 800, а из Code Review - все 666, прошедшие исходные проверки.

Отсюда фиксированный общий объём:
```text
800 (linux) + 800 (databases) + 800 (systems) + 666 (programming)
= 3 066 записей до очистки F1.4
```

Здесь `available_rows` означает **число строк, допущенных исходным загрузчиком после проверки обязательных текстовых полей**, а не полное количество публикаций на всех сайтах Stack Exchange.

**Ключевое ограничение:** метка `linux` означает, что пример взят из соответствующего сообщества; это не гарантирует, что истинная причина технической проблемы относится исключительно к Linux. Например, вопрос из Server Fault тоже может обсуждать Linux. Поэтому эти классы - **тематические метки источника**, между которыми возможны содержательные пересечения.

**Зачем этот шаг:** определить понятный `target` для обучения и одновременно не выдавать тематическую метку источника за безусловную экспертную диагностику.

### Шаг 4. Зафиксирована конкретная ревизия источника
Нельзя строить воспроизводимый эксперимент на расплывчатом условии «возьми текущую версию датасета». Если владелец набора обновит файлы, последующий запуск может получить другие записи.

Поэтому в `manifest.json` записан **ID датасета** и конкретная ревизия:
```text
Dataset:
flax-sentence-embeddings/stackexchange_titlebody_best_and_down_voted_answer_jsonl

Revision:
32151f5480872e6db89ae147e1d727266f574606

Seed: 42
```

Для каждого из четырёх архивов сохранён URL вида:
```text
https://huggingface.co/datasets/<dataset>/resolve/<revision>/<site>.jsonl.gz
```

Важна именно часть `resolve/<revision>/`: она фиксирует запрашиваемую версию.

При этом **revision и seed решают разные задачи**:
- **Revision** закрепляет версию источника.
- **Seed** помогает повторить детерминированную процедуру выбора записей при тех же исходных данных и алгоритме.
- **SHA-256** позволяет позднее проверить фактическое содержимое скачанного файла по его байтам.

**Зачем этот шаг:** сделать идентичность исходного корпуса явной, чтобы результаты разных запусков можно было сопоставлять.

### Шаг 5. Составлен manifest и учтены ограничения публикации
Собраны необходимые сведения в `data/raw/manifest.json`. Каждая запись источника содержит URL архива, ожидаемый локальный путь, SHA-256 и два счётчика: `available_rows` и `selected_rows`.

Упрощённая структура одного элемента:
```json
{
  "file": "data\\raw\\unix.stackexchange.com.jsonl.gz",
  "sha256": "<зафиксированная SHA-256 длиной 64 символа>",
  "available_rows": 6173,
  "selected_rows": 800
}
```

Полные URL и реальные SHA-256 находятся в manifest проекта. Пример выше нужен лишь для понимания структуры записи.

Отдельно зафиксировано лицензионное замечание: карточка датасета указывает **CC BY-NC-SA 4.0**, а в данной выгрузке нет достаточных сведений для индивидуальной атрибуции оригинальных постов и авторов. В ней отсутствуют прямые URL исходных вопросов и имена авторов. Указанный `source_url` относится к gzip-архиву, **не к конкретному сообщению Stack Exchange**.

Из-за этого считается невозможным свободное оформление исходных текстов и ответов в публичный GitHub-репозиторий. Публикуется код, описание источников, контрольные суммы и тесты на синтетических данных; сами Q&A-файлы остаются за пределами Git.

**Зачем этот шаг:** сохранить необходимую информацию о происхождении данных, не публикуя материалы с неразрешёнными вопросами лицензии и атрибуции.

### Шаг 6. Подготовлена автономная проверка provenance
Реализован модуль [`src/data/provenance.py`](../../src/data/provenance.py). Его задача - **не скачивать данные, а проверять корректность уже сохранённого описания**.

Работа разделена на несколько функций:
1. **`load_manifest(path)`** читает JSON и убеждается, что на верхнем уровне находится объект.
2. **`validate_manifest(manifest)`** проверяет ожидаемый ID, формат 40-символьной ревизии, `seed=42`, список полей, лицензионную запись и ровно четыре уникальных источника.
3. Для каждого источника проверяются корректность имени и пути к `.jsonl.gz`, соответствие URL зафиксированной ревизии, формат 64-символьного SHA-256 и допустимость счётчиков: `0 < selected_rows <= available_rows` и `selected_rows <= 800`.
4. **`verify_raw_files(manifest, root)`** применяется отдельно, если архивы уже лежат локально: пересчитывает SHA-256 по реальным байтам каждого файла и сравнивает его с manifest.
5. **`main()`** предоставляет командный запуск и печатает итог `PASS` либо понятное сообщение `FAIL`.

Отдельная деталь реализации - **нормализация путей**. В историческом manifest пути записаны с Windows-разделителями `\\`, но автоматические тесты GitHub могут работать на Linux. Проверяющий код приводит разделители к `/` для проверки допустимого пути, не изменяя сам manifest.

Если метаданные содержат неправильный источник, URL без закреплённой ревизии или небезопасный путь, код сообщает о нарушении контракта через `ManifestError`.

**Зачем этот шаг:** обнаружить изменения и ошибки provenance до того, как они повлияют на будущий ML-эксперимент.

### Шаг 7. Проверка корректных и намеренно испорченных случаев
После основной реализации написан [`tests/test_provenance.py`](../../tests/test_provenance.py). Было недостаточно проверить только «хороший» manifest: такой тест не показал бы, умеет ли программа обнаруживать ошибки.

Поэтому проверки устроены как набор сценариев:
- **Настоящий manifest:** убедиться, что описаны четыре источника, 3 066 выбранных записей и ожидаемые числа для всех четырёх классов.
- **Несовпадение идентичности:** поменять ID датасета, ревизию, seed, список полей или лицензионное описание и убедиться, что проверка отклоняет изменения.
- **Некорректный URL:** подставить вместо закреплённой ревизии `main` и проверить, что такой источник не допускается.
- **Ошибки списка:** повторить один источник или указать неизвестный/небезопасный путь.
- **Ошибки счётчиков и хеша:** поставить недопустимое число выбранных записей или SHA-256 неверного формата.
- **Проверка реальных байтов на синтетике:** создать четыре маленьких тестовых файла, рассчитать их SHA-256, успешно проверить и затем испортить один файл, чтобы получить ожидаемую ошибку.

Последний сценарий особенно показателен: он доказывает, что функция сравнения хешей обнаруживает изменение содержимого, но не требует скачивания чужих технических текстов.

**Зачем этот шаг:** проверить не только успешный путь, но и способность программы останавливать работу на неподходящих метаданных.

## 4. Как устроена проверка F1.2 при запуске

Разбор последовательности, которая выполняется при команде `python -m src.data.provenance` **без** параметра `--verify-files`.
1. Python открывает `data/raw/manifest.json`.
2. Функция `load_manifest` читает и разбирает JSON.
3. `validate_manifest` последовательно проверяет идентичность датасета, ревизию, поля, лицензионную запись, четыре источника, URL, пути, хеши и счётчики.
4. Если хотя бы одно условие нарушено, возникает `ManifestError`, после чего команда выводит `Dataset provenance: FAIL: ...` и завершается с кодом 1.
5. Если всё согласовано, программа показывает, что файловые SHA-256 **пока не проверялись**, и выводит сводку `Dataset provenance: PASS; sources=4; selected=3066; seed=42`.

Это принципиальное разделение : **проверить корректность написанного SHA-256 - не то же самое, что пересчитать SHA-256 файла**.

## 5. Схема: от постановки задачи к закреплённому источнику

```mermaid
flowchart TD
    A["Цель: классифицировать технические вопросы"] --> B["Выбираем Stack Exchange Q&A"]
    B --> C["Зафиксировать Hugging Face revision"]
    C --> D["4 сообщества и 4 тематические метки"]
    D --> E["Правило отбора: seed 42, не более 800 на источник"]
    E --> F["Manifest: 3 066 записей, URL, пути и SHA-256"]
    F --> G["Offline validate_manifest"]
    G --> H{"Архивы уже скачаны?"}
    H -->|Нет| I["PASS метаданных; байты не проверены"]
    H -->|Да, с --verify-files| J["Сверка SHA-256 четырёх файлов"]
    J --> K["Результат контроля целостности"]
    F --> L["Ограничения лицензии и атрибуции"]
```

**Главное на схеме:** решение о выборе данных и контроль provenance предшествуют обучению модели. Наличие корректного manifest позволяет описать вход эксперимента, но не заменяет реальную загрузку и проверку файлов.

## 7. Что подтверждено и какие ограничения

**Что сделано:** выбран конкретный технический корпус, описаны четыре тематические метки и исходный объём 3 066 записей, зафиксированы ревизия и правила отбора, подготовлен manifest, а код и тесты проверяют его согласованность. Публичные тесты не требуют оригинальных Q&A-текстов.

Четыре важных ограничения:
1. **Лицензирование и атрибуция.** Карточка датасета указывает CC BY-NC-SA 4.0, при этом исходный export не предоставляет индивидуальные URL и авторов постов. Поэтому чужие тексты не включаются в GitHub без отдельного разрешения вопросов распространения.
2. **Смысл меток.** `linux`, `systems`, `databases`, `programming` обозначают сообщество происхождения; тематические области могут пересекаться.
3. **Границы проверки.** `validate_manifest` проверка формы и значений метаданных; SHA-256 фактических файлов проверяется только через `--verify-files`.
4. **Воспроизводимость.** Seed сам по себе недостаточен. Необходимо сохранять версию источника и проверять содержимое скачанных архивов, иначе исходная выборка может измениться.
